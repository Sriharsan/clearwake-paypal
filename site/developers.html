01

Quickstart

Install

Clearwake runs on the Python standard library. You need Python 3.12 or newer and git. Docker is needed only for the network cut run. Clone with submodules, because the receipt and policy code is in vendor/verdock-core.

Open http://127.0.0.1:8810/console for the three screens (buyer agent, control room with the dispute ledger, receipt verifier). With no keys set, everything is a local run on the local provider: no PayPal call and no network call. Speak to it from a phone with python -m clearwake --phone.

Run scripts for Windows and for macOS or Linux are in the repository root.

02

Quickstart

Guard PayPal's Agent Toolkit

Clearwake adds what the toolkit leaves to you: limits, one request id per money move, a read of PayPal's record before any retry, and a signed receipt.

paypal_toolkit_tools is the tool list your agent framework got from PayPal's toolkit. guard() returns a list of the same length and order. Read and write tools come back as the same objects. The 8 tools that move money come back wrapped, with the same name, description and schema. The wheel carries what it runs on, so the install needs no git submodules and no vendor folder. It needs Python 3.10 or newer and nothing else.

The policy is the file shown under Policy file below. Limits in it are in cents. A prompt, a buyer message or a model reply cannot change it.

What each kind of tool gets

ToolsCountWhat guard does
Read and write tools, such as get_dispute, list_transactions, create_invoice39Nothing. The same objects, unchanged, no receipt.
accept_dispute_claim and create_refund2Reads PayPal's record first and takes the amount from it. Above the policy limit: held for a person, nothing sent. Above the approval line: a person approves that exact move. One request id from the hash of the move. After a lost reply the next call reads PayPal's record and never repeats a move that applied. A signed receipt for every call.
pay_order, send_invoice, send_invoice_reminder, record_payment_for_invoice, record_refund_for_invoice, activate_recurring_series6Held for a person unless the policy names the tool as an operation. A request id and a signed receipt either way. The guard cannot read their amount from one record, so a policy line with max_amount_minor for them holds the call.

A call that is stopped returns JSON text: {"clearwake_guard": {"state": ..., "detail": ..., "sent": false, "request_id": ...}}. A call that went through returns PayPal's own reply unchanged. A call that lost its reply raises the original error to the agent. Approve a held move with tools.approve(approval_id, by="your name"); tools.pending() lists the open requests. tools.verify() checks the receipt log offline against its own public key.

Or point your agent at Clearwake's MCP server

Install it as above (pip install git+https://github.com/Sriharsan/clearwake-paypal). Claude, ChatGPT, Cursor or any MCP client can then use Clearwake in place of PayPal's MCP server. It lists the same 28 PayPal tools with the same names and schemas. The money tools are guarded, the read tools pass through. The default backend is the local provider: no account, no network, nothing real to move.

To put it in front of PayPal's own MCP server on the sandbox, add "--backend", "paypal" to the args and set CLEARWAKE_SANDBOX_ACK=I_CONFIRM_SANDBOX_ONLY, PAYPAL_ENVIRONMENT=SANDBOX and a sandbox PAYPAL_ACCESS_TOKEN in the client's environment. Clearwake refuses to start without them. Details and the install check are in docs/MCP_SERVER.md.

Tested against the real list of 47 tools recorded in docs/paypal_mcp_tools.json, with no network (tests/test_guard_api.py). The wrapped tools were not run against the live PayPal sandbox, and the toolkit as recorded sends no PayPal-Request-Id, so protection against a repeat comes from the ledger and from reading PayPal's record before any retry. The rest of the guard is described in docs/TOOLKIT_GUARD.md, and the Break it page replays the recorded attacks.

03

Quickstart

Add sandbox keys

Create a sandbox app in the PayPal developer dashboard and put its client id and secret in a .env file at the repository root. Git ignores that file. Clearwake reads only these names from it, and a value already set in your environment wins.

  • PAYPAL_BASE_URL must be exactly the sandbox host. Clearwake refuses to start against anything else, so production cannot be reached by a typo.
  • CLEARWAKE_SANDBOX_ACK must be the exact text shown. Without it the sandbox gateway will not load.
  • PAYPAL_SANDBOX_CAPTURE_ID is the id of a COMPLETED sandbox capture that the refund cases use. A PENDING capture is refused.
  • Optional, for the dispatch proof setup only: HF_TOKEN. Optional for a local model: CLEARWAKE_LOCAL_AI_ACK, CLEARWAKE_LOCAL_MODEL_DIGEST, CLEARWAKE_LOCAL_LEDGER.

Never paste a key into a chat, a screenshot or an issue. The sandbox setup scripts (scripts/sandbox_setup.py, .ps1, .sh) write only the capture id back to .env.

06

Guide

Settle in conversation

While a dispute is at the INQUIRY stage, seller and buyer can still talk. A case settled here is not escalated to a claim, so PayPal charges no Standard Dispute Fee. Clearwake reads the dispute, lets the policy pick the amount, and sends one offer.

  1. The model may only choose a name: settle_by_offer, refund_within_limit, fight_with_evidence or escalate. The amount comes from the case and the policy, never from the model or the buyer's text.
  2. The policy decides. In policy/merchant.yaml, make_offer has a limit of 500 minor units (USD 5.00) and needs approval above 300 (USD 3.00).
  3. Clearwake calls POST /v1/customer/disputes/{id}/make-offer with a stable PayPal-Request-Id. PayPal refunds only if the buyer accepts. In the sandbox the buyer accepts in the Resolution Center.
  4. Clearwake reads the dispute back. Only PayPal's record can mark it settled: UNDER_REVIEW is PENDING, RESOLVED is VERIFIED.

Send the offer alone. PayPal refuses an offer after a seller message. This was seen on the real sandbox as 422 ACTION_NOT_ALLOWED_IN_CURRENT_DISPUTE_STATE. Clearwake now sends the offer without a message first, and a refusal is written to the receipts as it happened.

Result: PASS. USD 2.50 refunded to the buyer (refund 0TB11858A85953644), never a claim. These lines are from site/receipts/case-n-settle.ndjson.

Guide

Evidence before the deadline

Clearwake reads the dispute's seller_response_due_date and the links PayPal offers, and acts only on what PayPal offers. If the case is near the deadline, it escalates to the approval inbox with the time left instead of guessing.

  • Evidence comes from the record only: the PayPal order, the tracking, the mandate receipt, the dispatch receipt. The buyer's message is read as a claim to check.
  • Evidence goes to POST /v1/customer/disputes/{id}/provide-evidence as multipart. Part input is JSON {"evidences": [...]}. Each photo is an evidence-file part.
  • Send one merged evidence entry. PayPal needs an item_id when there are several entries, and a disputed item can carry none. Two entries (tracking and dispatch proof) were refused with ITEM_ID_IS_MANDATORY_FOR_MULTIPLE_EVIDENCES.
  • If the case has already moved to UNDER_REVIEW and PayPal no longer offers provide_evidence (item not received, dispute PP-R-SLI-10195419, stage CHARGEBACK, 31 Oct 2026), Clearwake sends the tracking note through provide-supporting-info instead.
  • Then it reads the dispute back. Evidence counts as sent only when PayPal's record shows it: clearwake.dispute.evidence_checked with dispatch_evidence_seen true.
08

Guide

Dispatch proof

When a buyer says only 2 of 3 items arrived, the best answer is a signed record of what went in the parcel. At packing, you photograph the open parcel. SAM 3 runs on your own machine and counts the items. Clearwake signs one receipt into your receipt chain.

One time setup of SAM 3

  1. On Hugging Face, request access to facebook/sam3 (needed) and facebook/sam3.1 (optional). Both are gated.
  2. Add HF_TOKEN= and your read token to .env. It is read only by the setup script and never printed.
  3. Run the setup. It installs CPU PyTorch and Meta's code into tools/sam/.venv and downloads 3.5 GB of weights next to the repository.

After the download, counting sets HF_HUB_OFFLINE=1 and works with the network unplugged. SAM 3 counts still photos. SAM 3.1 is Meta's video tracker and Clearwake does not claim it for photos.

Pack an order

--item is SKU=QUANTITY:PROMPT. The prompt is the word SAM looks for, and it matters: on the test photo, "book" found 3 notebooks and "notebook" found none. Every prompt run is listed in docs/RESULTS.md. Use --photo-note to say what a photo is when it is not your parcel. It is signed into the receipt.

The receipt clearwake.dispatch.recorded holds the order and capture ids, ordered and counted per item, the prompts, the SHA-256 of each photo, whether the parcel was sealed, the counter, the model, the device, the milliseconds, and the policy hash.

Strong or weak

When the dispute arrives, the Evidence agent checks the receipt. It is strong only if all of these hold: the receipt log verifies, counted equals ordered for every item, the parcel is sealed, a photo hash is on record, the tracking shows SHIPPED or DELIVERED, the order lines match, and the number the buyer wrote matches the order.

A weak proof is never sent. The policy settles by offer or escalates instead.

Mandate receipts

When an agent places an order for its owner, the buyer agent writes a signed mandate receipt into its own chain, with its own key. If the order is later disputed as unauthorised, the merchant's Evidence agent attaches that receipt, and anyone can verify it offline.

The buyer agent has a mandate: an owner, a budget, a per item cap, the merchants it may buy from and the categories it may buy. It refuses anything outside it. The receipt action is clearwake.buyer.mandate and its params are:

ParamMeaning
order_idThe PayPal order the agent paid for
merchantThe merchant id from the catalog
itemThe product id
price_minor, currencyWhat it cost, in integer minor units
budget_minor, per_item_cap_minorThe owner's limits that applied
allowed_categoriesThe categories the mandate allowed

Buy inside the mandate (a) signs the receipt. Refuse outside the mandate (b) makes no payment. The unauthorised order check (j) disputes an agent order and attaches the receipt, which verifies offline. All three run on local records. To run the buy inside the mandate against the sandbox, add --sandbox --order ORDER_ID with an order the sandbox buyer approved.

Guide

Reconcile an UNKNOWN

If PayPal does not answer, the action may or may not have happened. Clearwake does not guess and does not resend money. It holds the action as UNKNOWN, writes clearwake.refund.unknown, and keeps the reservation so the limits stay safe.

  1. Read PayPal first. Read the capture or refund record (GET /v2/payments/captures/{id}, GET /v2/payments/refunds/{id}) or the dispute (GET /v1/customer/disputes/{id}).
  2. Compare it with what you expected. Only an observed record that compares VERIFIED moves an UNKNOWN to VERIFIED. No record means it stays UNKNOWN.
  3. Only if the policy says retry: safe (evidence, messages), send again with the same PayPal-Request-Id, so PayPal answers with the first result and does not apply it twice. Refunds and offers are retry: never.
StateMeaning
VERIFIEDEvery compared field matches PayPal's record
MISMATCHAt least one compared field differs
UNKNOWNNo record, or a field is missing. Do not retry blind
PENDINGPayPal reports a status still in progress

The same case ran on the real sandbox as an injected fault: the real refund was sent and its reply withheld. Result: 1 refund at PayPal, the second call sent nothing, reconciled to VERIFIED. Dispatch proof submission 2 and submission 3 above show the same rule for evidence.

11

Guide

Run with the network cut

The network cut run (letter m) runs the agents on an internal Docker network. The egress gateway is the only service with a route out, and it allows only api-m.sandbox.paypal.com. The script then cuts the gateway's outside network in the middle of a batch.

--boundary-only runs only the boundary checks and leaves the stack up. It makes no sandbox call and sends no refund. Inside the container, CLEARWAKE_EGRESS=host:port points the PayPal transport at the gateway, and ambient proxy settings are never read.

  1. Builds the image and starts the gateway and Ollama.
  2. Checks the boundary: no direct route out, a host off the allowlist is refused and receipted, the local model answers inside.
  3. Runs the network cut run against the sandbox. After the first refund is verified, the gateway is disconnected. Refunds are held as clearwake.offline.held, not UNKNOWN, because the request never left.
  4. Reconnects. Clearwake reads PayPal first, then sends the held refunds with their original request ids.
  5. Verifies every receipt log in a container started with --network none.

Every number on the hosted site is read from a recorded run. The network cut as a local run uses a network switch in place of Docker, and its output says so.

    Reference

    Policy file

    The policy is a file the server reads at start. A model never reads or edits it, and no prompt, buyer message or chat can change it. It is YAML (a small subset) or JSON, parsed and checked by vendor/verdock-core/verdock_core/policy.py. Unknown keys are rejected. Amounts are integers in minor units (cents). Floats, yes, no, null, anchors and flow lists are rejected.

    KeyTypeMeaning
    versionintegerRequired. Must be 1.
    operations.NAME.leveltextRequired. Assist, Draft, Execute with Approval or Execute within Limits. Assist and Draft never execute.
    operations.NAME.max_amount_minorintegerOptional. Above it the action is refused.
    operations.NAME.approval_above_minorintegerOptional. Above it a person must approve that exact action.
    operations.NAME.currency3 capitalsOptional. Another currency is refused.
    operations.NAME.retrytextOptional. never (default) or safe.
    caps.per_customer_per_day_minorintegerOptional. A daily total per customer.
    egress.allow_hostslist of hostsOptional. The only hosts the egress gateway may reach. Without it nothing may leave.

    Each decision returns one of: within limits, approval required by level, approval required above threshold, above limit, currency mismatch, invalid amount, draft only or unknown operation.

    The policy hash is the SHA-256 of the checked policy as JSON with sorted keys and no spaces. It is written into the params of every receipt as policy_hash, so a receipt shows which rules were in force. Changing any level, limit, currency, retry rule or cap changes the hash.

    The code also has a hard cap of USD 5.00 per refund (LIMIT in clearwake/paypal.py) that no file can raise. The refund workroom reads a second file, policy/autonomy.json: refund.limit.max up to 5.00, approval_expires_seconds from 30 to 900, and retry must be never.

    Reference

    Receipt format

    Signed, hash chained action receipts in the format of draft-sahu-agent-action-receipts-00. One line of JSON per action. Ed25519 and SHA-256.

    FieldTypeMeaning
    step_idtextWhat step this is, for example PP-R-OBG-10196144:offer
    action_idtextWhat happened, for example clearwake.dispute.offer_sent
    paramsany JSONThe facts. Keys are sorted at every depth when signing.
    successtrue or falseWhether the action held up when checked
    ts_msintegerMilliseconds since the Unix epoch
    actorobjectOptional. agent and user, both text
    prev_hash64 hexSHA-256 of the exact bytes of the line before. Absent on line 1.
    public_key64 hexThe Ed25519 public key, 32 bytes
    signature128 hexThe Ed25519 signature, 64 bytes
    • Integers only. A non integer number anywhere in a line is rejected, so the Python and browser verifiers always agree. Money is in minor units.
    • Signed bytes: compact JSON of step_id, action_id, params, success, ts_ms, actor (agent, then user) and prev_hash, in that order, leaving out any that are absent.
    • Other members are added. They are not signed, but the next line's prev_hash covers them.
    • Limit: a log with its newest lines removed still verifies. Keep the head digest somewhere else to catch that.

    One line of the file, pretty printed. In the file it is one line, and the signature is one 128 character string.

    Reference

    API reference

    The calls Clearwake makes, each with a request you can copy and the response that was recorded on the real sandbox. Replay shows a recorded response again. It sends nothing. Responses list only the fields that were read back in the run, not the full body. Set ACCESS_TOKEN from POST /v1/oauth2/token with your client id and secret, use a new UUID for REQUEST_ID, and set the other shell variables a request names (NOTE, NOTES, TRACKING) before you run it. Bodies are written as here documents, so each variable expands inside the JSON.

    • GET /v2/payments/captures/{id}
    • POST /v2/payments/captures/{id}/refund
    • GET /v1/customer/disputes/{id}
    • POST /v1/customer/disputes/{id}/make-offer
    • POST /v1/customer/disputes/{id}/provide-evidence
    • POST /v1/customer/disputes/{id}/provide-supporting-info
    • POST /v2/checkout/orders/{id}/track

    GET /v2/payments/captures/{id}

    Read a capture. Clearwake does this before every refund, and again to reconcile. A capture that is not COMPLETED is refused.

    POST /v2/payments/captures/{id}/refund

    One refund, in USD, at most 5.00. The request id is created once and reused on any retry the policy allows. Refunds are never retried.

    GET /v1/customer/disputes/{id}

    Read a dispute. Clearwake acts only on the actions PayPal lists in its links, so this read decides what happens next.

    POST /v1/customer/disputes/{id}/make-offer

    Offer the buyer a refund to settle at the INQUIRY stage. Send it alone: PayPal refuses an offer after a seller message. PayPal refunds only if the buyer accepts.

    POST /v1/customer/disputes/{id}/provide-evidence

    Evidence as multipart: part input is JSON, each photo is an evidence-file part. Send one merged entry, because PayPal needs an item_id when there are several.

    POST /v1/customer/disputes/{id}/provide-supporting-info

    Notes only, no files. PayPal offers this once a dispute is under review and no longer offers provide-evidence.

    POST /v2/checkout/orders/{id}/track

    Add tracking to an order. Clearwake reads trackers back from the order when it builds evidence.

    Every path the transport allows

    Every call goes to https://api-m.sandbox.paypal.com. The transport in clearwake/paypal.py allows only these paths: HTTPS, no query string, no redirects, no proxy except the egress gateway, a 15 second timeout, and a response of at most 262,144 bytes. Any other path is refused before it is sent. POST calls carry a PayPal-Request-Id.

    Method and pathUsed for
    POST /v1/oauth2/tokenClient credentials token
    GET /v2/payments/captures/{id}Capture read before every refund, and to reconcile
    POST /v2/payments/captures/{id}/refundOne refund, USD, at most 5.00
    GET /v2/payments/refunds/{id}Read the refund back
    POST /v2/checkout/ordersOne time setup order (sandbox)
    GET /v2/checkout/orders/{id}Order lines and trackers
    POST /v2/checkout/orders/{id}/captureCapture a setup order
    POST /v2/checkout/orders/{id}/trackAdd tracking to an order
    GET /v1/customer/disputesList disputes
    GET /v1/customer/disputes/{id}Read a dispute and the actions PayPal offers
    POST /v1/customer/disputes/{id}/make-offerOffer a refund to settle at INQUIRY
    POST /v1/customer/disputes/{id}/send-messageMessage the buyer at INQUIRY
    POST /v1/customer/disputes/{id}/provide-evidenceEvidence from the record, multipart, one merged entry
    POST /v1/customer/disputes/{id}/provide-supporting-infoNotes once a dispute is under review
    POST /v1/customer/disputes/{id}/accept-claimAccept and refund inside the limit
    POST /v1/customer/disputes/{id}/adjudicateSandbox only: finish a test dispute

    Error explorer

    Search a PayPal error or a Clearwake outcome. Each entry says where it was seen, the cause and the fix. Only errors seen in real runs or raised by the code are here.

    1. 422 ACTION_NOT_ALLOWED_IN_CURRENT_DISPUTE_STATE

      Real sandbox, settled by offer, PP-R-OBG-10196144, 3 Nov 2026

      Cause
      An offer was sent after a seller message. PayPal allows an offer only in an inquiry that waits for the seller.
      Fix
      Send the offer alone, first. Clearwake does this now and writes the refusal to the receipts as clearwake.dispute.refused_by_paypal.

    2. 400 INVALID_REQUEST ITEM_ID_IS_MANDATORY_FOR_MULTIPLE_EVIDENCES

      Real sandbox, dispatch proof, PP-R-UKF-10195772, 3 Nov 2026

      Cause
      Two evidence entries were sent, and the disputed item shows no item id.
      Fix
      Send one merged entry with the tracking, the notes and the documents together.

    3. 400 No permissions to set target_client_id

      Real sandbox, 31 Oct 2026

      Cause
      Creating a dispute for the buyer with a buyer assertion. The app's token has disputes/create, update-seller and read-seller, not update-buyer.
      Fix
      The sandbox buyer opens disputes in the Resolution Center. Clearwake handles them from there.

    4. 400 TRANSACTION_NOT_ELIGIBLE

      Real sandbox, 31 Oct 2026

      Cause
      The same create call without the assertion.
      Fix
      Same as above.

    5. capture status PENDING

      Real sandbox, network cut, second run, 31 Oct 2026

      Cause
      The configured capture was PENDING, and the capture read before the refund refused it.
      Fix
      Put a COMPLETED capture in PAYPAL_SANDBOX_CAPTURE_ID.

    6. Capture preflight failed. Nothing was sent.

      Real sandbox, 31 Oct 2026, first run of the three refund runs

      Cause
      Clearwake will not fetch a token in the moment before a POST. The capture read failed, so the refund was held.
      Fix
      Run it again. Nothing reached PayPal, so there is nothing to reconcile.

    7. Offline: the request did not leave this network.

      Network cut run, 31 Oct 2026

      Cause
      The egress gateway refused the tunnel or nothing could be reached. The request never left.
      Fix
      It is held as clearwake.offline.held. After reconnecting, Clearwake reads PayPal first, then sends with the original request id.

    8. The sandbox response is uncertain. No automatic retry was sent.

      Lost reply: reconciled refund of 31 Oct 2026, and dispatch proof submission 2 of 3 Nov 2026

      Cause
      The request may or may not have been applied.
      Fix
      State UNKNOWN. Read PayPal first. Retry only if the policy says retry: safe, with the same PayPal-Request-Id.

    9. 403 from the egress gateway

      Network cut run, example.com through the gateway

      Cause
      The host is not in egress.allow_hosts.
      Fix
      Expected. Only api-m.sandbox.paypal.com passes.

    10. PAYPAL_BASE_URL must be exactly the sandbox host

      code Raised at start by the code

      Cause
      The base url is not https://api-m.sandbox.paypal.com.
      Fix
      Set PAYPAL_BASE_URL to the sandbox host. Clearwake never runs against anything else.

    11. Explicit sandbox-only acknowledgement is required

      code Raised at start by the code

      Cause
      CLEARWAKE_SANDBOX_ACK is not set to I_CONFIRM_SANDBOX_ONLY.
      Fix
      Set it in .env.

    12. UNKNOWN

      code Clearwake outcome

      Cause
      There is no observed record, or a compared field is missing. The action may or may not have happened.
      Fix
      Do not retry blind. Read PayPal's record and compare.

    13. MISMATCH

      code Clearwake outcome

      Cause
      At least one compared field differs from PayPal's record.
      Fix
      Treat it as not done as expected. Read the record and decide with the owner.

    14. PENDING

      code Clearwake outcome

      Cause
      PayPal reports a status still in progress, for example a dispute UNDER_REVIEW after an offer.
      Fix
      Wait and read again. Only RESOLVED counts as settled.

    15. above limit

      code Policy decision

      Cause
      The amount is higher than max_amount_minor for that operation.
      Fix
      Nothing is sent. Change the file and restart, or let the owner decide.

    16. approval required above threshold

      code Policy decision

      Cause
      The amount is above approval_above_minor.
      Fix
      It waits in the approval inbox. One approval, one exact action.
